분석 기준은 [PR #271](https://github.com/oneot/elevate/pull/271)이 병합된
`main`의 `2a86295421823293a2b538b7027e3e20321ba051`이다.
아래 내용은 저장소의 주요 실행 경로와 로컬 검증 결과이며, 운영 Azure 구성이나
기업 네트워크를 재검증했다는 의미가 아니다.

## 동작과 계약

### 공개 사이트

- 기존 공개 API의 15초 요청 제한, GET 일회 재시도, 취소 소유권 및 60초 성공 캐시는 유지한다.
- 활동 영상은 기존 기본 목록을 없애거나 새 스냅샷으로 만들지 않는다. API 실패 시 기본
  목록을 표시하고 있음을 알리며, 재시도는 `v`, `category`, `q`를 유지한다.
  정상 API가 빈 목록을 반환하면 기본 목록으로 덮어쓰지 않는다.
- `?preview=local`은 API를 호출하지 않는다. 미리보기로 전환하면 진행 중인 조회를 취소한다.
- 달력의 이전/다음 이동은 월말과 윤년에도 정확히 인접 월로 이동한다. 일정 데이터와
  선택·연결 의미는 바꾸지 않는다.
- PR #272 당시에는 챗 토큰만 선조회하고 UI·WebChat을 처음 열 때 로드하여 이후
  닫기/열기에서 같은 인스턴스를 보존했다. 첫 열기 지연에 대한 후속 사용자 요청에 따라
  현재는 사이트 진입부터 비동기 모듈 준비와 실제 연결을 시작한다.
  WebChat 청크 약 3.51 MB(gzip 약 944 kB)는 여전히 존재한다.

### 관리자

- pathname이 바뀌면 내부 페이지 상태를 새로 생성하되 TopBar/Sidebar는 유지한다.
  기존 글에서 새 글로 이동할 때 제목·본문·게시 상태·첨부 세션이 잘못 재사용되지 않는다.
- 썸네일과 본문 이미지 업로드를 개수로 추적한다. 모든 이미지 업로드와 기존 첨부
  업로드가 끝나기 전에는 저장하지 않는다.
- `Headers`, 객체, 튜플 형태의 사용자 헤더와 MSAL 토큰을 함께 보존한다.
  401의 토큰 갱신은 유지하지만 POST/PUT/DELETE를 자동으로 재전송하지 않는다.
- 요청 취소는 네트워크 오류와 구별하고, 오류 본문은 한 번만 읽는다.
  잘못된 성공 JSON과 본문 전송 실패도 구별한다.
- 청크 로딩/렌더 오류는 페이지 안에서 알리고, 자동 새로고침하지 않는다.
  다른 경로로 이동하면 오류 경계가 초기화된다.

### 서버

- 정상 요청의 URL, 응답 필드, 상태 코드, 인증 경계는 유지한다.
  잘못된 JSON은 컨트롤러 실행 전에 기존 `{code, message, correlationId}` 형태의
  400으로 반환한다. 인증 검사는 본문 파싱보다 먼저 수행한다.
- 본문 없는 DELETE는 클라이언트가 `Content-Type: application/json`을 보내도 기존처럼
  허용한다. 본문 읽기 자체의 실패는 500과 Azure Functions 오류 로그로 남긴다.
- 페이지/limit의 정수 범위와 기본값은 유지한다. `1.5`, `20posts`, `1e2` 등을
  앞부분만 정수로 해석하지 않고 400으로 처리한다.
- `postContent.js`는 기존 SAS를 제거하고 고유한 전체 URL마다 서명한 뒤 한 번에
  치환한다. `image.png`와 `image.png-large.png`가 서로 손상되지 않으며,
  Markdown 닫는 괄호·외부 URL·첨부파일 다운로드 이름을 유지한다.
- 활동 영상의 실제 category 파티션을 우선하는 기존 방식은 유지하고, category가
  없는 기존 문서는 저장된 `partitionKey`, 이어 기존 `activityVideo` 기본값을 사용한다.
  DB 구조를 이전하거나 저장 문서를 일괄 변환하지 않는다.

## 성능과 용량

동일 Node 22 환경의 Vite 빌드로 비교했다. 초기 목록 크기는 HTML 진입과 기본
`CategoryPosts`(관리자 리뉴얼 후 `AppPosts`) 화면의 정적 JavaScript 의존성을 중복 없이 합친 값이다.

| 측정 | 기준 코드 | 변경 후 |
| --- | --- | --- |
| Admin 초기 목록 JavaScript | 약 1.08 MB | 545,136 bytes, 약 49% 감소 |
| 해당 파일별 gzip 합계 | 약 321 kB | 157,303 bytes |
| 초기 목록에서 편집기 청크 로딩 | 포함 | 제외 |

단순 `React.lazy`만으로는 충분하지 않았다. 수동 청크가 공용 React JSX/CommonJS
런타임을 Tiptap에 포함해 초기 진입이 다시 편집기를 끌어왔다.
`vite.config.js`는 패키지 내부와 CommonJS proxy까지 같은 런타임 청크로 분류한다.
`check:bundle`은 기본 목록의 정적 의존성, 편집기 유입, 600 KiB 한도를 확인하며
경계값 614,400/614,401 bytes도 테스트한다.

기준 코드의 추적 파일 합계는 **22.47 MiB**, 로컬 Git pack은 **2.69 GiB**였다.
Git 이력 크기를 배포 산출물이나 첫 페이지 다운로드 크기로 해석하지 않는다.
대형 원본 이미지·기존 콘텐츠·이력은 삭제하지 않았으며, 이 PR이 Git 이력을
축소했다고 주장하지 않는다. `dist`, `node_modules`, 성능 로그는 커밋하지 않는다.

### 웹챗 후속 개선 (2026-10-18)

기준은 PR #272가 병합된 최신 `main`의 `e9df408d5d9a6d72395338a7a7ced90f09dee787`이다.
이전 변경을 확장하지 않는 별도 웹챗 수정이며, HTTPS·공개 API 캐시·Admin·Server와
보류된 VPN/DNS/라우팅·호스팅/배포 구성은 변경하지 않는다.

`ChatWidget`이 앱 수명의 세션을 소유하고, `webChatSession.js`가 모듈/토큰 병렬 준비,
연결 상태, 취소, 제한 시간, 재시도와 정리를 관리한다. 창 표시 및 라우트 수명과 분리하여
`/all` 직접 진입, 닫기/재열기, `/elevathon` 왕복에서도 연결과 대화 store를 유지한다.
WebChat 4.18.1 / DirectLineJS 0.15.5의 실제 `activity$` 구독이 연결을 시작하도록 유지한다.
토큰만 선조회하거나 `createDirectLine` 객체만 만드는 것을 연결 완료로 간주하지 않는다.
구독 시작을 한 microtask 뒤로 보내 StrictMode의 취소된 첫 effect가 SDK를
`Connecting`에 남기는 경쟁도 방지한다. 클릭이나 idle 대기는 추가하지 않는다.

토큰은 캐시에 방치하지 않고 준비 즉시 연결에 사용한다. SDK의 15분 자동 갱신과
대화 ID·최신 토큰·watermark를 사용한 재연결을 유지하며, 만료된 특정 대화의 서버 측
복구 계약을 새로 가정하지 않는다. 만료/종료 후 새 대화는 사용자 선택으로만 시작하고
이전 화면 기록은 보존한다. 새 대화는 이전 봇 문맥을 이어받는다는 의미가 아니다.
상세 제한 시간과 오류/재시도 동작은 [Web README](../../Elevate.Web/README.md#웹챗-연결과-가독성)에 기록했다.

다음은 로컬 Chromium에서 **실제 SDK + 모의 HTTP/WebSocket**을 사용한 단일 비교 실행이다.
WebChat 화면 모듈 1.2초, 토큰 2초, Direct Line 연결 응답 3초를 지연시켰다.
게시글 화면 표시 후 8초 뒤에 채팅을 열었으며 시간은 페이지 진입 기준이다.
외부 요청은 차단하고 로컬 모의 게시글·이미지·대화만 사용했다.

| 관측 | 기준 main | 변경 후 |
| --- | --- | --- |
| 게시글 화면 표시 | 0.975초 | 0.487초 |
| Direct Line 연결 요청 시작 | 10.899초, 클릭 후 | 2.216초, 클릭 전 |
| 채팅 클릭 | 8.976초 | 8.488초 |
| 클릭 → 첫 모의 봇 답변 표시 | 5.394초 | 0.111초 |

변경 후 화면 표시 직후 0.487초에 연 별도 실행에서는 **4.866초의 잔여 대기**가 있었다.
준비 중에는 그 상태를 표시했고, 페이지는 토큰 응답 전에 표시됐다.
이 수치는 운영 실측, 통계적 성능 보장 또는 네트워크 지연 0이라는 주장이 아니다.
느린 네트워크/기기에서는 초기 다운로드·파싱 비용과 준비 중 클릭의 대기가 남는다.
첫 열기 대기를 줄이기 위해 방문 직후부터 네트워크를 사용한다는 명시적 우선순위 변경이다.
프로덕션 빌드에서도 SDK는 초기 정적 의존성이 아닌 약 3.51 MB의 별도 비동기 청크다.

헤더·본문·봇/사용자 말풍선·입력 영역·하단 안내의 실제 배경을 불투명하게 했다.
1440×1050, 390×740, 667×375 화면에서 글과 큰 색상 이미지가 있는 목록 위로 열어
배경 비침이 없고 입력창/토글이 화면 안에 남는 것을 확인했다. 작은 높이를 넘던
430px 최소 높이도 제거했다. 사용한 일반 텍스트 색 조합의 대비는 최소 4.55:1이며,
본문은 17.85:1, 사용자 말풍선은 10.35:1이다. wrapper opacity나 글자 흐림으로 해결하지 않았다.

로컬 브라우저에서는 실제 SDK의 첫 연결·기존 인사 이벤트 한 번 전송·모의 메시지 송수신,
토글/라우트 이동, 15분 토큰 갱신, 장시간 숨김 복귀의 동일 대화 재연결, 403 만료 시 정리와
명시적 새 대화/기록 보존, StrictMode를 확인했다. 고의적인 만료 오류는 표시·로그로 남긴다.
프로덕션 산출물의 로컬 preview에서도 같은 연결·갱신·재연결·만료와 화면 동작을 확인했다.
Node 22에서 Web Vitest **84개(웹챗 관련 26개 포함)**, 기존 소스 회귀 8개, lint, SEO 검사,
Vite 프로덕션 빌드 및 외부 API 없는 SEO shell 생성을 통과했다.
운영 봇에 테스트 메시지를 보내지 않았으며 원본 첨부·실사용 대화·토큰을 산출물에 포함하지 않았다.
SDK 내부의 React 개발 모드 경고와 큰 청크/Speech SDK 빌드 경고는 기준 코드에도 있으며
이번 수정에서 SDK 전면 교체나 의존성 버전 변경으로 숨기지 않는다.

### 관리자 리뉴얼 (2026-10-20)

기준은 `main`의 `61b12ea`다. 관리자 프런트엔드만 바꾸며, Server API·데이터와 운영 설정은 변경하지 않는다.
공개 사이트는 분류 규칙 두 줄(아래)만 바뀐다. 위 관리자 항목 중 일정·활동 영상 편집 관련 내용은
이번 리뉴얼로 관리자 화면에서 제거됐다. 해당 서버 API와 공개 사이트 표시는 그대로다.

- **제거**: Sub category(Agenthon, Update, MEE, 행사 소식, 프로그램 소식) 목록·작성,
  달력 이벤트 편집·게시글 연결, Management(활동 영상) 목록·편집 화면과 서비스, 미사용 `EventDatesEditor`.
  관리 대상이 아닌 category 글을 주소로 열면 편집 양식 대신 안내만 표시한다.
- **앱 분류**: 관리자 목록을 공개 블로그의 13개 앱으로 맞췄다. 2026-10-20 공개 API 대조 결과
  M365 22건은 M365 3·Word 5·PowerPoint 7·Forms 5·OneDrive 2건이다. Copilot Studio 11건은
  Copilot Studio 6·GitHub 4·Azure 1건이다. 분리된 M365 글 19건은 모두 시리즈와 앱 태그를 함께 가진다.
  관리자는 Web 규칙을 복제하고(`Elevate.Admin/src/constants/apps.js`) Web 원본과의 일치를 테스트한다.
  새 글은 앱의 서버 category에 저장하고 앱 태그를 붙인다(예: Word → `m365` + `word`).
- **Web 규칙 변경**: GitHub/Azure는 기존 slug 목록으로만 나뉘어 새 글을 배치할 수 없었다.
  그래서 `CATEGORY_SPLIT_RULES`에 `tag: 'github'`, `tag: 'azure'`를 추가했다. 추가 전 규칙에서도 위 공개 글 33건의
  분류가 같음을 `Elevate.Web/tests/category-split-rules.test.js`로 고정했다.
  태그 'GitHub'를 가진 Copilot Studio 글은 `agent-to-website` 하나이며 이미 slug로 GitHub다.
- **디자인**: 공개 블로그(`DocsShell`/`DocsHero`/`DocsList`)와 같은 헤더·문서 바·앱 내비게이터·
  히어로·카드 그리드를 관리자용 CSS(`ea-*`)로 구현했다. 관리자 목록 API 요약에는 썸네일이 없다.
  그래서 카드 이미지 자리는 공개 사이트가 썸네일 없는 글에 쓰는 앱 유리 타일로 채운다.
- **인증**: `redirectUri`/`postLogoutRedirectUri`는 현재 origin이다. `VITE_AZURE_AD_REDIRECT_URI`는
  같은 호스트일 때만 적용한다. 로그인 계정이 없으면 화면 진입 시 한 번만 로그인으로 이동하고, 헤더에서 로그아웃한다.
  로그아웃 직후 같은 탭에서는 자동으로 다시 로그인시키지 않는다.
- **기존 결함 수정**: `main` 운영 빌드에서 `/posts/new`가 Tiptap 오류
  (`Cannot read properties of null (reading 'cached')`)로 열리지 않았다. React가 숨겼던 편집기를 다시 연결할 때
  이미 파괴된 Tiptap 인스턴스로 `getHTML()`을 호출한 것이 원인이다. 파괴된 인스턴스를 건너뛰게 했고,
  `<Activity>`로 같은 경로를 재현하는 회귀 테스트를 추가했다. 기존 글을 불러오지 못하면 빈 양식을 열지 않는다.
  빈 양식을 저장해 기존 내용을 덮어쓰는 위험이 있었기 때문이다.
- **번들**: 초기 목록 JavaScript는 545,418 → 556,137 bytes(gzip 157,386 → 162,449)로 600 KiB 예산 안이다.
  앱 아이콘·유리 타일 이미지(약 330 KB)는 JS에 인라인하지 않는다.

모의 API와 로컬 브라우저로 화면, 새 글·편집 흐름, 자동 저장 복구를 확인했다.
실제 Entra 로그인, 운영 API 저장, 사용자 지정 도메인 접속은 배포 후 확인 대상이다.

## 회귀 검증과 배포 경계

아래 세 앱 검증 수치는 PR #272 당시 기록이다. 웹챗 후속 변경은 별도 Web 회귀와
실제 SDK 로컬 브라우저 확인으로 검증하며 Admin/Server 구현은 변경하지 않는다.

- Web: Vitest 59개, 기존 소스 검사 8개, lint, SEO 검사, Vite 빌드와 오프라인 SEO shell 생성.
- Admin: Vitest 28개, 기존 소스 검사 4개, lint, 잠금 파일 클린 설치, 빌드 및 초기 목록 예산 검사.
- Server: 132개 통과, Azure 연결 검사 2개는 기본 실행에서 제외. 기존 실패하던
  lowercased route parameter/partition fallback도 통과한다.
- 세 GitHub Actions 워크플로를 actionlint로 검사했다. PR에서도 세 앱을 독립적으로 실행한다.
- SEO fixture는 루프백 HTTP 서버만 사용한다. 기존 메타데이터 shell을 확인하며
  게시글 본문을 빌드 산출물에 복제하지 않는 것도 검사한다.

배포에서 이미 사용하던 `REQUIRE_API_ROUTES=true`는 이제 API 오류, 잘못된 페이지 정보,
기존 20페이지 한도 초과를 명시적으로 실패 처리한다. 선택적 로컬 빌드는 기존 정적
경로 shell을 생성할 수 있다. 실제 배포·운영 설정 변경·자동 병합은 수행하지 않는다.

## 남겨 둔 항목

- VPN 경유 Azure 공개 API 접속 장애는 **미해결·보류**다. 기기 VPN/DNS/라우팅,
  기업 정책, 프록시/호스팅, 콘텐츠 스냅샷으로 우회하지 않는다.
- 정책·아키텍처 기준 문서와 `infra/`의 완전한 복구는 Azure 실배포 상태와 운영 설정의
  교차 확인이 필요하다. 이번에 복구한 PLAN을 완전한 인프라 복구로 간주하지 않는다.
- MSAL/Entra의 실제 로그인·권한, Cosmos 파티션 구성, SAS 발급/만료 및 게시·삭제의
  실운영 통합 검증은 하지 않았다. 기존 개발용 토큰/키 override, Blob 삭제의
  best-effort 처리, 서명 요청 수 최적화도 별도 정책·운영 확인 대상이며 이번에 변경하지 않는다.
- 프레임워크 전면 이관, 데이터/게시 구조 변경, 전체 의존성 버전 갱신과 Git 이력
  재작성은 하지 않는다. WebChat의 큰 지연 청크 등 기존 의존성 경고는 숨기지 않는다.
